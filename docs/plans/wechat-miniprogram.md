小程序以个人主体的产品范围设计。所有页面使用小程序组件；产品范围不依赖 `web-view`。主体、服务类目和正式发布资格需要在微信后台核验，代码完成不代表平台审核通过。

### 3.2 规则对战的执行方式

- 游客使用共享 TypeScript 引擎在设备上计算，数据保存在小程序本地工作区。
- 登录用户联网调用现有 Java 规则引擎，结果由后端保存。
- 登录用户不需要断网模拟；请求失败显示真实错误并保留编辑状态，不自动生成另一场设备端比赛。
- 小程序发起规则对战时使用现有 `simulationMode: 'local'` 协议值。该值在登录请求中表示规则引擎，执行位置是服务器。
- 保持现有常规时间比赛的每队 240 分钟、单人最多 48 分钟等统计约束，不借助客户端迁移改变比赛公式。
- 此次开发保留 Web 的 AI 能力与调用流程。

### 3.3 共享包与中文文案

- 复用当前仓库，两个客户端共用现有 Java 服务和数据库。
- `packages/core` 只包含纯数据、类型、比赛规则、阵容校验和数据展示逻辑，不依赖 React、DOM、小程序 API、存储、网络或 i18n。
- 小程序界面使用中文常量；Web 继续通过现有 i18n 获取文案。
- 内置阵容工厂接收名称和描述参数。小程序传入中文常量，Web 传入 `i18n.t(...)` 的结果。
- `player-catalog-chinese-names.json` 是目录数据，继续作为中文名称的单一来源。球员定位与简介的翻译不属于本次工作。

## 4. 用户流程与页面行为

### 4.1 页面组织

建议底部入口为“球员”“阵容”“对战”“我的”。页面职责如下：

| 页面           | 必须提供的行为                                                                             |
| -------------- | ------------------------------------------------------------------------------------------ |
| 球员列表       | 搜索英文名、中文名和已有搜索字段；按位置过滤；按综合评分、三分能力、薪资排序；分批展示目录 |
| 球员详情       | 展示姓名、中文姓名、位置、能力值、身高体重、定位和简介；允许进入阵容选择流程               |
| 我的阵容       | 展示当前身份拥有的阵容；创建阵容并进入编辑页；选择已有阵容                                 |
| 阵容编辑       | 修改名称和描述；添加、移除球员；调整位置、首发和激活状态；展示保存状态和校验提示           |
| 球员选择       | 展示候选球员、已选状态、搜索与过滤；防止同一球员重复加入                                   |
| 对战           | 选择两套不同阵容，校验后发起规则模拟；展示进行中、失败和成功状态                           |
| 战报列表、详情 | 展示比分、阵容名称、最佳球员和技术统计；详情使用历史快照                                   |
| 我的           | 当前账号、微信绑定状态、登录入口、退出入口、分享管理入口                                   |
| 登录与账号绑定 | 微信登录；已有账号认证并绑定；新账号建立；游客数据导入选择                                 |
| 分享详情       | 按访问标识读取有效快照；展示过期、撤销、不可用状态；提供适用的复制动作                     |
| 我的分享       | 列出本人创建的分享、到期时间和状态；允许撤销                                               |

阵容编辑采用适合手机的独立页面和选择页面。页面、表单、提示与导航需要适配键盘、安全区域、返回操作和后台恢复。

小程序对球员能力编辑与自定义球员创建保持只读：只读取、展示并使用已有账号从 Web 保存的球员覆盖和自定义球员，用于其阵容与规则对战，不提供编辑与创建入口。

### 4.2 阵容与保存规则

- 沿用当前成员模型：`playerId`、`position`、`starter`、`inactive`。
- 阵容最多 15 人、激活球员最多 13 人、首发最多 5 人；同一球员不得重复，非激活球员不能设为首发。
- 允许保存不完整的阵容草稿；发起比赛时须满足至少 5 人、恰好 5 名首发且覆盖 PG、SG、SF、PF、C。
- 阵容名称及描述遵守当前后端约束：名称非空且最多 120 字符，描述最多 1000 字符。
- 登录用户连续编辑同一阵容时，保存请求保持顺序，较早响应不能覆盖较晚编辑。
- 开始对战、创建分享之前，必须等待涉及的阵容保存成功。
- 数据异步加载后，重新校验当前阵容及主客队选择仍有效，沿用现有修复行为。
- 页面离开或切换后台时，不得把未成功保存的编辑显示为已保存。对未保存草稿提供恢复或明确离开提示。
- 当前后端阵容接口提供读取和保存；整套阵容删除未列入本次已确认需求。移除成员属于阵容编辑。

### 4.3 游客工作区

- 初次进入可以浏览目录、使用内置阵容、编辑阵容和完成规则对战。
- 小程序使用独立于浏览器的本地存储；两者的游客数据不会自动互通。
- 保持 `GuestWorkspace` 的稳定 UUID、版本、时间、`hasUserProgress`、球员、阵容、战报等语义。
- 内置示例初始化不计入用户实际进度；存在用户数据时不得重新初始化并覆盖。
- 新账号建立后，存在实际游客进度则自动导入；登录或绑定已有账号时，由用户选择是否导入。
- 导入成功后才清空对应游客工作区；失败保留全部数据，允许重试。跳过导入也保留游客工作区。
- 沿用 `/guest-imports` 事务和幂等规则：同一工作区导入同一账号可重试，导入其他账号返回冲突。
- 退出账号时清理该账号的会话与内存数据，恢复独立游客状态。异步请求返回时必须校验仍属于同一会话。
- 游客战报沿用当前最多保留 20 场、有效期 30 天的行为；登录战报沿用服务器 30 天保留规则。
- 微信身份建立与游客导入分别处理。导入失败不得触发重复建号。

## 5. 账号与微信身份

### 5.1 已确认的身份原则

- `users.id` 继续作为业务数据归属的唯一内部用户标识。
- 微信身份通过独立表绑定到现有用户，球员、阵容、战报等表继续引用同一用户。
- 旧用户通过现有账号认证后绑定微信；新用户通过微信建立账号，并有能够登录 Web 的方式。
- 绑定冲突必须明确提示；不按照昵称、展示名自动合并用户或转移数据。
- 后端签发并验证项目自己的 JWT；所有 owner 信息由服务端认证上下文取得。

### 5.2 建议完整流程

1. 用户主动进入微信登录，客户端调用微信登录能力取得临时 `code`，提交至 Java 服务。
2. Java 服务使用服务端配置的 AppID 和 AppSecret 向微信交换身份。客户端提交的 openid 或用户 ID 不能作为认证依据。
3. 已绑定身份直接登录对应内部账号。
4. 未绑定身份返回短期、一次性的身份确认凭证，用户选择“绑定已有账号”或“创建新账号”。不要在选择前自动创建业务账号。
5. 绑定已有账号需要成功验证其用户名和密码；创建新账号的凭据方式见第 12 节建议。
6. 在事务中建立用户与微信身份关系，成功后签发 JWT，再处理游客导入。
7. 账号页面展示绑定状态。账号切换清理上一账号的缓存和请求状态。

建议身份表字段：`id`、`user_id`、`provider`、`appid`、`openid`、可选 `unionid`、`created_at`。建立 `(provider, appid, openid)` 唯一约束，并明确同一用户在同一 AppID 下的绑定数量约束。默认建议每个用户绑定一个微信身份，须确认产品选择。

`unionid` 按可选字段处理。绑定冲突返回结构化错误；不能因为并发请求导致重复用户或身份占用。身份确认凭证使用服务端随机值，服务端保存摘要、过期时间和使用状态；不能直接携带明文微信会话密钥。凭证在绑定事务成功时消费，同一成功操作的重试应能识别结果；已消费凭证不能绑定另一个用户。

当前 `users.username`、`password_hash` 在数据库中可空，但客户端 `AuthUser.username` 和 JWT 颁发流程按已有账号形态使用。新增微信账号必须同步设计这些字段，不能只插入微信身份后留出不可用的 Web 账号。

AppSecret、微信返回的会话密钥、密码与完整登录凭证不能进入日志、源码或小程序构建产物。缺少微信配置时应明确显示该登录能力未配置，现有 Web 密码登录继续正常工作。

### 5.3 建议接口

接口前缀为 `/api/v1`；下表均为新增建议，路径可以在实现时统一调整。

| 接口                         | 认证与行为                                                                |
| ---------------------------- | ------------------------------------------------------------------------- |
| `POST /auth/wechat/exchange` | 接收一次性 code；返回已有账号会话，或短期身份确认凭证及需要选择账号的状态 |
| `POST /auth/wechat/bind`     | 验证短期凭证及已有账号认证；原子建立绑定并返回会话                        |
| `POST /auth/wechat/register` | 验证短期凭证；创建账号与绑定；返回会话及新账号标记                        |
| `GET /auth/identities`       | JWT 认证；只返回当前用户的绑定状态，不返回微信密钥                        |

现有 `/auth/login`、`/auth/register`、`/auth/me` 保持兼容。安全配置只放行明确需要匿名访问的接口，避免对整个 `/auth/**` 放行。对凭证交换、密码验证及绑定失败增加合理限频，具体阈值通过配置管理。

## 6. 独立分享

### 6.1 已确认的行为

- 分享对象是阵容或战报，内容来自分享时的数据快照。
- 独立记录保存访问标识、到期状态与撤销状态，使用独立创建、读取、复制和撤销接口。
- 分享页面只展示该条内容；创建分享不发布社区帖子。
- 创建后修改原阵容或球员，不改写已经生成的快照。再次分享当前内容应创建新的快照。
- 名称、描述等公开文本经过审核；审核失败或审核服务故障时不创建可访问分享。
- 访问有效分享的人可以看到对应公开快照。只有所有者能够管理或撤销自己的分享。
- 分享过期或撤销后，重新读取和复制都应失败；已经复制至接收者账号的阵容是独立数据。

### 6.2 建议数据结构与权限

建议新增 `content_shares` 表，包含内部 ID、所有者、对象类型、来源 ID、不可预测的访问 token 摘要、快照版本、jsonb 快照、创建时间、到期时间、撤销时间、创建幂等键。来源对象 ID 应明确区分阵容的客户端键和数据库 UUID。若要求所有者再次分享同一记录或创建请求重试时返回同一地址，还须保存可由服务端解密的 token；只有摘要无法恢复分享地址。加密字段只供服务端使用。

后端根据当前用户和来源 ID 读取并生成快照，不能信任客户端传入的 owner 或任意完整公开数据。创建分享与复制请求可使用幂等键；相同用户、相同键重试返回已有结果，相同键配合不同请求内容返回冲突。

公开响应只返回展示必需内容，不泄露所有者的其他阵容、登录凭据或 AI 配置。访问 token 仅提供该分享的读取能力，管理接口仍须 JWT 和所有权校验。公开内容无全站列表与评论接口。到期、撤销检查在服务端读取和复制时执行，不能只依靠前端按钮或定时清理。

快照字段建议：

| 类型 | 快照内容                                                                 |
| ---- | ------------------------------------------------------------------------ |
| 阵容 | 名称、描述、成员位置及角色、各球员展示资料与能力值、目录标识             |
| 战报 | 双方名称、比分、球员展示字段、技术统计、比赛创建时间、到期时间、引擎版本 |

审核必须针对最终保存的同一份快照。可在数据库事务外审核冻结内容，再在事务内保存该内容并验证来源版本，防止审核期间修改名称导致未审内容被发布。公开战报中来自用户的阵容名及自定义球员名称也需要纳入审核。

### 6.3 创建、访问与复制

- 建议创建分享要求登录，并以已经保存的服务器数据为来源。游客先完成登录及导入，再继续创建分享；具体产品选择见第 12 节。
- 创建分享完成后，客户端取得页面路径和访问标识，再呈现微信分享按钮；接收页面可独立恢复数据，不能依赖发送者的内存状态。
- 建议有效分享允许游客查看，复制阵容需要登录；认证结束后恢复原分享目标。
- 复制阵容创建接收者拥有的新阵容和新 ID，不修改发送者数据。
- 分享允许包含自定义球员和能力覆盖的阵容；复制时在接收者账号下新建球员记录或覆盖，不复用原作者的私有 ID，快照中的能力值保持不变。禁止无提示地把快照中的球员替换成另一套能力值。
- 战报支持查看与分享；复制接口只用于阵容，战报不写入接收者的本人比赛记录。
- 撤销后清理当前详情显示和客户端缓存。接收者在页面重新显示时重新验证有效性。
- 分享后的源数据删除、战报清理和快照保留期限按第 12 节确定，分享不得意外延长私人战报保留时间。

### 6.4 建议接口

| 接口                               | 行为                                                         |
| ---------------------------------- | ------------------------------------------------------------ |
| `POST /shares`                     | JWT；提交类型、来源 ID、幂等键；所有权检查、快照、审核后创建 |
| `GET /shares`                      | JWT；分页读取本人分享管理信息                                |

## 7. 前端架构与文件改造

小程序前端框架：采用 Taro + React + TypeScript，选型已经用户确认。 小程序与现有 Web 放在同一个仓库，共享纯业务逻辑、数据结构、后端和数据库。选择 Taro 的理由是延续项目已有的 React 与 TypeScript 开发方式，便于复用业务逻辑。小程序页面使用 Taro 组件，路由、生命周期、网络请求和存储由小程序端适配。现有 Web 页面组件仍需根据小程序交互重新实现。具体依赖版本在开发前核验兼容性并锁定。

### 11.4 工程与验证方式

- 规则测试随模块迁移，覆盖现有真实目录及确定性输入；对业务不变量测试，不复制实现来构造预期结果。
- core 构建不得要求 DOM、小程序全局对象、React 或 i18n。Web 和小程序分别完成类型检查与生产构建。
- 后端迁移和接口集成使用真实 PostgreSQL，验证既有数据库升级及新库初始化。
- 微信登录、分享及存储使用真实开发者工具和真机验证，不使用伪造微信响应冒充完成。遵守仓库禁止 mock 的规则。
- 真实输入操作覆盖中文输入、清空、连续输入、保存失败、返回、切换后台及恢复。遵守用户关于视觉工具的限制，使用允许的交互与日志方式记录证据。
- 回归 Web 的游客、密码登录、球员编辑、阵容、规则和 AI 对战、社区、国际化；小程序改造不能损坏这些已有能力。
- 小程序能力验收至少包含开发者工具及 iOS、Android 真机；缺少设备、凭据或平台权限时注明具体未验收项，不能报告全部完成。

当前仓库已迁移为 npm workspaces（`apps/web`、`packages/core`、`packages/client`），在仓库根目录执行：

```bash
npm test
npm run typecheck
npm run build
npm run format:check
git diff --check
```

`npm run build` 先对 core、client、web 分别运行 `tsc --noEmit`，再执行 `vite build apps/web`。阶段 3 引入小程序后，typecheck、测试与构建脚本需覆盖 `apps/miniprogram`，并在交接文档给出最终准确命令。

后端使用 Java 21，在 `backend` 目录执行 `mvn test`。集成测试配置位于 `backend/src/test/resources/application-test.yml`，当前连接本地 5432 端口的 `basketball_gm_test`；Compose 数据库默认映射 5433，不能混淆生产或开发数据与测试数据库。根据本机工具安装配置 JAVA_HOME 和 Maven。

Docker 路径变更后执行配置校验、镜像构建及健康检查，验证 Web 静态资源和 `/api` 转发。记录实际日期、命令、结果和未验证事项。向远端 `main` 推送前必须完整运行前后端全部测试并全部通过。
