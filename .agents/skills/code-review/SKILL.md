# Code Review

按根目录 `AGENTS.md` 执行。先确定操作类型：独立审查、意见汇总、修复后复核。用户只讨论流程或查询 Skill 时，不启动代码审查。

本 Skill 通过仓库文件传递状态，不依赖特定模型、CLI、子 agent API 或全局技能。Codex 和 Kimi Code 显式读取本路径即可采用同一流程；自动加载能力须另行验证。

## 1. 确认任务与授权

1. 阅读用户指令、`AGENTS.md`、当前计划及相关需求和 accepted decisions。按任务定位必要架构与代码，确认审查范围和验收条件。
2. 核对 branch、HEAD、暂存、未暂存和未跟踪文件，确认 worktree 写入归属。记录实施者、审查者及会话标识；汇总时再确定汇总负责人。
3. 使用稳定的任务名称，如 `wechat-login-stage4`；同一任务修复后的 commit 变化不改变目录名称。
4. 明确可写路径。仅聊天输出或限定单一报告文件时，遵守该限制，任务信息记录在允许的输出中；其余任务状态文件保持原样。审查授权不包含自动修复。
5. 写入报告前读取 [报告与问题记录](references/reporting.md)，确定轮次、报告路径及编号。已存在的旧格式报告按原路径保留，迁移另行授权。

完成条件：目标、验收依据、操作类型、参与者、写入边界和输出位置均明确。缺失信息仅在影响审查结果时询问。

## 2. 固定审查版本

### 已提交变更

- 将基线和待审引用解析为完整 commit SHA，记录 Base Commit、Reviewed Commit 和实际比较命令。
- 对明确的两个版本使用 `git diff <base-sha> <reviewed-sha>`；用户要求从分叉点审查时，先求 `git merge-base` 并记录实际比较起点。明确是否包含分支已有的其他提交。
- 检查范围内是否存在未提交内容；按用户范围纳入下一种模式或明确排除，不能用 HEAD 代表它们。比较为空时报告无待审差异，不产生完整实现已通过的结论。

### 包含未提交变更

- 记录 HEAD、暂存和未暂存差异、未跟踪文件清单及审查范围。`git diff` 单独执行会遗漏未跟踪文件，需逐项读取范围内的新文件。
- HEAD 只标识起点。为实际输入建立 Snapshot ID 和文件清单，记录相对路径、SHA-256、删除项，以及配置、依赖锁文件和需求文档等相关输入；排除项写明原因。记录采用的比较命令。
- 审查期间冻结这些输入。开始与结束时核对清单；内容变化后重新确定快照、复查受影响发现及验证，未覆盖部分保持待审。
- 多位审查者需要相同内容时，使用已授权的本地提交或可复现的独立快照，并核验文件清单一致。创建 worktree 不会自动包含未提交修改。提交、复制敏感配置等动作仍受用户授权限制；无法固定输入时报告版本条件未满足。
- 摘要仅用于识别内容；重现审查还需要保留对应代码。快照位置与可用性必须记录，忽略目录中的本地材料不保证下一位审查者可访问。快照及报告不包含真实凭据。

完成条件：审查对象可识别且可复现，同轮各审查者的代码与需求输入一致。

## 3. 独立审查

1. 使用未参与本次实现的上下文，读取需求、规则和代码。独立发现阶段不读取其他审查报告或实施者的自我评价；已经接触这些内容时如实记录上下文来源，不能声称完全独立。
2. 检查需求符合程度、正确性、安全、数据完整性、并发与错误路径、架构边界及相关回归。每项发现写清触发条件、影响、对应版本中的位置、依据和证据；将事实、推断、待验证假设分开。
3. 根据当前脚本执行有意义的针对性验证。记录实际命令、版本、环境、结果与局限；历史测试结果单独标注。遵守仓库的真实验证和禁止 mock 规则。
4. 验证会生成构建文件、缓存或修改数据库时，使用本人拥有的检出目录和隔离的测试资源。并行审查者分别拥有 branch、worktree、输出文件及可能被修改的运行资源；无法隔离时串行执行。
5. 只报告可说明影响的问题；风格偏好与可选建议单独标记。已核对无问题项说明覆盖范围，未验证项说明原因。文档与实现存在差异时单独列出证据。
6. 按引用文件的格式交付本轮原始报告，重新核对代码快照。完成后的报告保留原文，后续更正通过新报告关联。

默认由一位独立审查者执行。任务要求多位审查者时，各自完成上述步骤后再汇总；额外审查不可用时记录缺口，不能声称完成双重审查。实施者自行检查可提供验证材料，独立审查仍需独立上下文执行。

完成条件：报告绑定实际审查版本，每项发现可追溯，验证及覆盖缺口明确，原始结果已经独立形成。

## 4. 汇总意见

1. 读取待汇总报告，核对任务、代码快照、需求版本和覆盖范围。不同版本的发现先按当前代码重新核验，再注明适用版本；不能直接视为同轮结论。
2. 按根因、触发条件和影响去重，建立稳定问题编号并保留所有来源。仅一方发现的问题同样核实；发现数量及双方同意均不构成正确性证明。
3. 对分歧记录双方证据，进行针对性检查或真实复现。需求不明确或风险接受需要用户决定时，保留待确认状态及具体问题。
4. 指定负责人更新问题清单和当前入口。实施者接收修复事项并记录回复；原始报告不随汇总改写。

完成条件：所有原始发现均有映射或明确处置，重复项保留来源，未解决分歧可见，当前入口指向有效记录。

## 5. 修复后复核

1. 实施者在获准修复后，记录问题编号、修改位置、修复版本和真实验证结果，将问题标记为 `FIXED_PENDING_REVIEW`。
2. 独立审查者固定新的 Reviewed Commit 或 Snapshot ID，检查原始触发路径、修复差异及受影响的相关回归。复核可以读取原始报告，记录本轮覆盖范围。
3. 通过后提供证据并标记 `VERIFIED`；失败或修复不完整时设为 `OPEN`，保留原因。缺少必要环境或证据时维持待复核状态。
4. 新发现使用新编号；原问题再次出现时恢复原编号并保留此前复核记录。汇总负责人依据复核报告更新清单。
5. 最终结论明确适用版本、审查范围、未解决问题、用户已接受风险及验证缺口。局部复核只支持局部结论；修复版本中的其他变更需要相应审查覆盖。

完成条件：修复声明均有复核结果或明确待办，审查结论与覆盖范围相符，下一位 agent 可以从当前入口继续。
