# 报告与问题记录

本文件定义持久化记录格式。代码审查、汇总和复核步骤见上级 `SKILL.md`；用户限制输出路径时，在允许的输出中保留必要字段。

## 文件职责

所有路径以仓库根目录为基准；`<task>` 使用稳定任务名称，`<reviewer>` 使用工具名称，多实例时附加可区分的会话标识。

| 路径                                         | 内容                                                   | 写入者         |
| -------------------------------------------- | ------------------------------------------------------ | -------------- |
| `docs/REVIEW_FEEDBACK.md`                    | 当前任务、待审版本、问题状态计数、详细记录链接和下一步 | 指定汇总负责人 |
| `docs/reviews/<task>/round-01-<reviewer>.md` | 第一轮独立审查报告                                     | 对应审查者     |
| `docs/reviews/<task>/round-02-<reviewer>.md` | 第二轮审查或修复复核报告                               | 对应审查者     |
| `docs/reviews/<task>/issues.md`              | 去重后的问题、来源、当前状态和证据                     | 指定汇总负责人 |

例如 `docs/reviews/wechat-login-stage4/round-01-kimi.md`。同轮编号用于相同待审代码和需求快照；修复后的版本进入新轮次。单一审查者也使用此结构，并维护从原始发现到问题清单的映射。

完成后的原始报告保持不变。内容纠正通过新报告说明原报告路径、发现编号、纠正依据及适用版本；仅因报告更正而代码未变时，可以保留原轮次并增加 `-correction-01` 后缀。写入前检查目标文件是否存在，避免覆盖其他会话的结果。

任务完成后保留目录。当前入口转向新任务时保留上一任务的链接；延期项有稳定引用、负责人与后续处理条件。已有 `REVIEW_FEEDBACK.md` 为完整报告时，先保留原文，获得迁移授权后才能改变其职责。

## 原始报告字段

### Metadata

- Task、Round、Mode：`independent | consolidation | verification`。
- Reviewer：工具、会话标识；Implementer：实施者标识；独立上下文情况及已读取的其他报告。
- Date：包含时区的审查时间。
- Branch、Worktree、Base Commit、Reviewed Commit：使用完整 SHA；未提交审查的 Reviewed Commit 写 `N/A`，另记 HEAD。
- Snapshot：未提交审查必填 Snapshot ID、内容保存位置、相对文件清单与摘要、删除项、排除项及开始/结束核对结果。
- Scope：纳入与排除的变更、比较命令；Requirements：需求和验收来源及版本。
- Write Scope：允许写入的文件；原始报告无需把实现文件列为可写。

### Findings

每项发现使用报告内稳定编号 `R01`、`R02`，包含：

- Severity：`blocker | major | minor`，以及判定理由。
- Location：实际审查版本的文件路径与行号；必要时附符号名。
- Trigger / Impact：触发条件、实际行为、预期行为和影响。
- Basis：需求或规则位置；正确性缺陷可引用接口契约或代码不变量。
- Evidence：已确认事实、代码推断、实际复现结果及尚未验证部分。
- Repair Direction：修复需要满足的行为与建议验证，不自动扩大实现范围。

严重度依据影响确定：`blocker` 表示当前范围中必须先排除的安全、数据或核心流程阻断；`major` 表示影响需求或重要行为的缺陷；`minor` 表示影响有限的缺陷。可选改进放入单独的 Suggestions，不混入缺陷计数。

### Coverage and Validation

- 已核对项：明确检查了哪些路径，以及证据覆盖边界。
- 文档差异：文档位置、实现证据、影响；没有发现时明确说明。
- 每条验证包含 Command、`PASS | FAIL | NOT RUN`、实际版本、必要环境、结果及局限。复现出缺陷时分别说明进程退出结果与业务判定。
- 未验证项：缺少什么条件、影响哪项结论。历史验证标明日期和版本。
- Verification 模式逐项记录来源编号、修复版本、检查路径、证据及复核结果；发现新问题时新增本报告编号。

### Conclusion

使用 `CHANGES_REQUIRED | INCOMPLETE | PASS`：存在尚未解决且未获用户批准延期的已确认缺陷时为 `CHANGES_REQUIRED`；其余情况下，必要审查或验证缺失、仍有待确认或待复核问题时为 `INCOMPLETE`；当前范围审查完成、已确认缺陷均复核通过或已有用户明确批准的剩余风险处置，且没有上述证据缺口时可为 `PASS`。同时存在缺陷与覆盖缺口时，两者均须列出。

`PASS` 必须附适用版本、范围、用户已批准的例外及未覆盖的平台验收。技术缺陷不会因用户接受风险而变成已修复；交付是否允许仍遵守仓库其他门禁。独立报告的 `PASS` 只代表该审查者覆盖范围，汇总结论还需核对全部报告和问题清单。

## 问题清单

文件顶部记录 Task、当前待审版本、汇总负责人、报告列表、总体审查结论及下一步。每项问题使用任务内稳定编号 `I001`、`I002`；跨任务引用必须包含任务路径。

每项记录包含：标题、严重度、所有来源报告路径及 `Rxx`、适用版本、当前状态、处理负责人、实施者回复、修复版本、验证证据、复核者和复核报告链接。合并发现时保留各自的触发条件与证据，不因相同文件位置就视为同一问题。

| 状态                   | 使用条件                       | 所需证据或决定                             |
| ---------------------- | ------------------------------ | ------------------------------------------ |
| `OPEN`                 | 已确认、尚未完成修复或复核失败 | 原始发现或复核失败证据                     |
| `NEEDS_CONFIRMATION`   | 证据不足、事实分歧或需求待确认 | 争议内容与待执行检查或待用户决定项         |
| `FIXED_PENDING_REVIEW` | 实施者声明完成修复             | 修复版本、修改说明及实际验证               |
| `VERIFIED`             | 独立审查者确认修复有效         | 复核版本、报告与证据                       |
| `DISMISSED`            | 发现经核验不成立               | 审查者的反证；需求解释涉及取舍时附用户决定 |
| `DEFERRED`             | 用户明确同意延期或接受剩余风险 | 用户决定、剩余影响、负责人及后续处理条件   |

单独一方的否认不能关闭问题。汇总负责人根据可追溯证据更新状态，不能代替独立复核。保留关键状态变化的版本、原因和证据链接，不记录聊天过程。

`NEEDS_CONFIRMATION`、`FIXED_PENDING_REVIEW` 和未获用户批准的延期均不能计为已解决；`DEFERRED` 单独计数，不能计为已修复。审查完成与问题修复完成分别说明。

## 当前入口

`docs/REVIEW_FEEDBACK.md` 只维护当前任务与历史任务入口、当前 Reviewed Commit 或 Snapshot ID、汇总负责人、各状态计数、`issues.md` 与报告链接、总体审查结论、验证缺口和下一步。计数及结论从清单核对，不复制问题正文和测试日志。

新任务初始化前核对旧入口是否仍有未解决问题；保留其任务链接和后续处理位置。入口更新、问题清单更新均由一个负责人串行完成，审查者只提交自己的报告与更正材料。
